# Distress Mode — design only
Non-destructive, no media capture initially. No PAM integration or shutdown action deployed.

NORMAL -> DISTRESS_TRIGGERED -> DISTRESS_BOOT_REQUIRED -> DISTRESS_RECOVERY_SESSION -> NORMAL only after owner recovery and subsequent normal reboot. Persist transitions atomically, versioned, boot-bound and replay-aware. Log activation without recording credentials. Interrupted shutdown/power loss must retain the stricter state. Errors cannot silently clear it.

TPM slots remain intact. Strong auto-unlock suppression needs an initramfs-visible gate with anti-tampering/rollback properties and an actual trusted unlock path; ordinary /var/lib state is inaccessible before root unlock, while a plain ESP flag is tamperable. TPM NV is a design candidate, not permission to provision it now.

Owner recovery requires evidence of manual LUKS unlock and separate normal authentication. A distress credential must never return normal PAM success. PAM changes require isolated tests across SDDM, Niri lock and console; rate limiting, secret handling and failure semantics need review. No secondary plaintext password database.

Future optional evidence needs explicit consent, visible indicators, local protected storage and retention. No covert capture or uploads. Restore only the recorded pre-distress policy, with conflict detection if it changed meanwhile; do not overwrite concurrent legitimate changes.

## Offline state reducer implemented
policies/distress.py implements NORMAL, TRIGGERED, BOOT_REQUIRED, RECOVERY_SESSION and RESTORE_PENDING as immutable versioned transitions. It does not read credentials, persist state, execute shutdown, modify TPM/LUKS/PAM, or run at boot.

A trigger immediately creates a strict state. A prepared shutdown remains strict. New boots from triggered/recovery states require fresh recovery evidence; power loss cannot preserve owner authentication across boots. Manual unlock, owner authentication and power-only device evidence must all be explicitly true in the same recovery boot. A subsequent owner-requested normal reboot prepares restoration but does not yet permit TPM. Only a different boot with restoration verified and the original policy digest unchanged returns to NORMAL. Concurrent policy changes retain strict state; the original digest is never overwritten. Retriggering from recovery reasserts protection.

State sequence and boot IDs support adapter checks but do not themselves prevent persisted-state replay. Evidence booleans are requirements for a future trusted adapter, not authenticated inputs. permits_tpm is only a local policy predicate: it MUST NOT be connected to cryptsetup without state provenance, device checks and all other boot protections. Replayed NORMAL state is an unresolved storage threat. Missing/corrupt state never grants local permission.

Required integration contract: persist and verify the strict transition before acknowledging a trigger or initiating shutdown; if persistence fails, do not report success. Do not publish NORMAL until restoration succeeds. Verify old/new policy and authenticated boot identity at every adapter boundary. Prove crash consistency and antirollback behavior in a disposable environment before touching laptop authentication. An interrupted normal reboot with a committed restore request requires a reviewed recovery decision; the current offline model allows restoration only when its explicit verification input is true.

Seven reducer tests cover the successful cycle, same-boot replay refusal, power loss in every strict phase, each recovery precondition, strict boolean handling, policy conflicts, illegal events, corrupt state and retriggering. All 37 project Python tests pass. These are policy tests, not tests of durable storage, PAM, real shutdown or TPM enforcement.

## Durable transaction prototype (undeployed)
policies/distress_store.py implements bounded canonical state encoding and a two-part commit contract. The caller must own a trusted private directory with trusted ancestors and serialize authorized transitions; the store does not authenticate the caller or replace the reducer. It writes a0600 temporary file, fsyncs it, atomically replaces state.json and fsyncs the directory, then compare-exchanges an independent witness from the exact previous digest to the new digest. Verification requires identical witness reads around the file read and an exact file digest match. Missing, malformed, unsafe, stale or mismatched state is unavailable and must select manual recovery.

A trigger may be acknowledged or shutdown requested only after commit verification succeeds. Before file publication an interrupted unacknowledged trigger leaves the old state. Between durable file publication and witness commit, disagreement denies normal trust. After witness commit, a lost acknowledgement leaves the strict state committed. No failed transaction automatically resets a witness or treats absence as NORMAL. Initial provisioning is explicit and refuses existing/incomplete state. Sequence increments and the original policy digest are checked. An authorized caller must obtain each next state from the reducer; the storage layer alone does not validate owner credentials or legal phase transitions.

The witness interface is a required trusted-backend contract, not a TPM implementation. Tests use memory and file witnesses ONLY as fixtures. Replaying both state and a software witness remains possible; no production rollback security is claimed. A hardware backend must supply appropriate authentication, durable update semantics and serialization, be accessible before root unlock, and resist reset/replay by the relevant adversary. TPM NV compare-exchange is not assumed to be a native primitive; its concrete protocol remains to be designed/reviewed. Old authorized boot-image bypass also remains unresolved.

Ten storage tests cover durable reopen, all three commit boundaries, witness failure, replayed NORMAL, stale witness/writer, policy changes, malformed/missing/symlink files, canonical encoding and the full reducer cycle. Boundary tests include actual child-process exit before cleanup with a durable test-only witness, as well as injected exceptions. These are process-crash tests, not physical power-loss or TPM durability tests. No host state directory, disk key, authentication stack, shutdown behavior or boot image was changed.
